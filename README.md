# Учебные примеры навыков

Комплект показывает, как разделить работу над небольшой задачей между тремя
ролями. Инструкции навыков написаны на английском, пояснения и пример — на русском.

| Навык | Ответственность |
|---|---|
| [Project Manager](project-manager/SKILL.md) | Сформулировать задачу, согласовать границы и проверить завершение. |
| [Feature Developer](feature-developer/SKILL.md) | Реализовать согласованное поведение и проверить его. |
| [Feature Reviewer](feature-reviewer/SKILL.md) | Проверить изменения, найти конкретные дефекты и пробелы в проверках. |

[Общий процесс](project-manager/references/workflow.md) хранит правила, которые
используют все три роли. Инструкции конкретного проекта имеют приоритет.

## Как начать

1. Прочитайте один `SKILL.md`: обратите внимание на `name`, `description`, шаги
   работы и ожидаемый результат. Описание помогает выбрать навык, основной текст
   задаёт действия, ссылки ведут к общим правилам.
2. Возьмите небольшой учебный проект с известной командой проверки. Прочитайте
   его `AGENTS.md`, если он есть, и выберите одну задачу с наблюдаемым результатом.
3. Пройдите пример ниже: планирование → реализация → ревью → проверка завершения.
   Трекер задач, контейнеры и отдельные агенты для этого не обязательны.

Для запуска через инструмент, поддерживающий навыки, используйте отдельное
учебное окружение. Размещайте три папки навыков рядом, сохраняя их имена и
`project-manager/references/workflow.md`: относительные ссылки зависят от этой
структуры. Не заменяйте одноимённые навыки своего рабочего окружения.

## Сквозной пример

Исходный проект — список задач. В нём уже есть добавление задач и переключение
их состояния между выполненным и невыполненным.

**Запрос:** «Добавь фильтр, который показывает только невыполненные задачи».

**Project Manager** сначала описывает согласованный результат:

```text
Задача: фильтр невыполненных задач.
Результат: пользователь может скрыть выполненные задачи.
Границы: существующий список; без удаления задач и изменения формата хранения.
Критерии готовности:
- По умолчанию видны все задачи.
- При включении фильтра видны только невыполненные задачи.
- После выключения фильтра снова видны все задачи.
- Выполненная при включённом фильтре задача исчезает из видимого списка.
- Для пустого результата показано понятное сообщение.
Проверка: список с выполненными и невыполненными задачами; переключение фильтра
и состояния задачи; существующие проверки проекта.
```

Это пример требований, согласованных для упражнения. Конкретный интерфейс
следует существующим элементам управления проекта; существенные неизвестные
требования обсуждаются до реализации.

**Feature Developer** находит список и его состояние, использует существующие
компоненты, добавляет фильтрацию и проверяет критерии готовности. В передаче
результата указывает изменённые файлы, выполненные проверки и ограничения.

**Feature Reviewer** читает требования и изменения. Например, если фильтр
вычисляется только при его переключении, недавно выполненная задача может
остаться на экране. Замечание должно указать место в коде, последовательность
действий и последствия. Если такого дефекта нет, придумывать замечание не нужно.

**Project Manager** сопоставляет результат с критериями готовности, возвращает
найденные дефекты на исправление и сообщает, что проверено. Слияние или публикация
выполняются в рамках уже полученного разрешения либо после отдельного согласия.

При одном исполнителе ревью служит самопроверкой. Для независимого ревью дайте
другому человеку или агенту требования, финальные изменения и результаты проверок.

## Как адаптировать

Начните с команд, соглашений и критериев готовности своего проекта. Добавляйте
специальные правила после конкретной потребности. Длинную инструкцию, которая
нужна только в отдельном случае, можно вынести в `references/` и указать, когда
её читать. Общие правила храните в одном месте, сохраняя рабочие ссылки.
